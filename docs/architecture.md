# Polaris: architecture

## Scope and boundaries

Browser-first **strict TypeScript + Vite + Babylon.js WebGL2**, in a single package. The atlas, the first scout-exploration slice and a serverless two-player turn exchange (ADR-005) are implemented, not the full first-playable match. Pure `src/game` owns generation, commands, pathfinding, faction fog and the match package (replay plus checksums). Use **Vitest in Node** for domain tests and **Playwright** for browser behavior.

| Directory | Responsibility | Must not contain |
| --- | --- | --- |
| `src/game` | Definitions, seeded generation, immutable expedition state, commands, movement/fog, match packages (replay log and checksums); later saves/AI | DOM, Babylon objects, wall-clock time, renderer state |
| `src/exchange` | Turn codes (compress, encode, decode links/files) and the browser-storage adapter for a running match | Game rules, Babylon objects; storage is injected, never reached through globals |
| `src/rendering` | Babylon scene, pure voxel construction/meshing (`voxels.ts`), camera, heightfield picking adapter | Authoritative gameplay rules or independent tile state |
| `src/ui` | Inputs, validation feedback, inspector, HUD, messenger panel | Simulation logic or direct mutation of domain state |

Dependencies point toward `src/game`. A small composition entry point wires adapters together. Rendering and UI consume domain snapshots/events and submit intents; neither determines authoritative outcomes.

## Planned target domain and compatibility

The [complete design](game-design.md#target-status-and-baseline) and [delivery plan](roadmap.md#detailed-target-delivery-plan) preserve the whole #20 → #21 → #22 → #24 → #29 → #31 foundation, including browser, hex voxels and messenger, integrated with #33/#34 and save reliability #47 on main at `c6c4cad`. The ADRs below describe implemented foundation contracts, not completed target gameplay. This section owns technical contracts only; rules, catalogs and balance status belong in game design. [Current application captures and verification](../README.md#current-verification-and-screenshot-provenance) identify their exact source and environment; they do not replace the historical performance benchmark or validate target gameplay.

### Authoritative state and commands

Keep all outcomes in pure `src/game`, with integer economy, explicit IDs, stable neighbour/job orders and serializable state machines. Costs, yields, abilities and prices use validated versioned definitions, never UI-local state or render-derived heights. Separate player identity from tribe definitions so mirror choices retain independent ownership, commands, budgets and research.

Canonical per-water-hex depth is implemented by G1/#53 in generator v5; its presentation and inspection consume that immutable data. Planned state covers typed classes/tribes, health/movement/action/counter budgets, public objectives/streaks, fortifications/occupation/original city owner, six resource balances, finite ruin inventories, local food/hunger, assignments/pins, project reservations and paid-cost receipts, carried founder provisions, embarked state and retained vessel capability, Landing/Harbour projects, military debt, research project/per-technology progress and ability charges/expiry.

Version serializable commands for attack (including explicit civilian attack), entrench, rest, embark/disembark, ability, beacon activation, improvement/dismantling, assignment, project cancellation, territorial claim/transfer and supply orders. Occupation and completion transitions are explicit logged domain outcomes. UI-local selection/animations are never authoritative.

Removal, permitted capture advance and ownership transfer resolve atomically before defeat checks; no observable intermediate entity/owner gap. A rejected command changes neither state, sequence, log nor RNG.

The [complete target ending sequence](game-design.md#complete-proposed-own-ending-sequence) owns gameplay order. Implement it with one stable snapshot, deterministic reservations/one-pass transfers and stable completion ordering. Preview and resolution share the same arithmetic and information policy, not independent simplified simulations. Public objective events must not expose adjacent hidden terrain/units. Visibility-safe contact stops and line-of-fire use canonical domain coordinates, never Babylon rays.

## ADR-001: browser stack

**Decision:** strict TypeScript, Vite, Babylon.js, WebGL2, one package.

| Alternative | Tradeoff and reason not selected |
| --- | --- |
| Godot native | Strong editor and native pipeline. Current Godot 4 C# projects cannot export to web; web export requires the Compatibility renderer and WebGL2, not Forward+/Mobile rendering parity. Those constraints favor the TypeScript browser stack here |
| Three.js renderer | Flexible, smaller rendering abstraction; more camera, picking, batching, and tooling assembly than Babylon for this prototype |
| Unity | Mature tooling, but heavier browser delivery and proprietary terms require a current legal/commercial terms review before any adoption |
| Bevy/Rust | Attractive ECS and native performance; Rust/WASM integration and browser tooling add complexity before gameplay needs justify it |

Revisit Godot if native desktop/mobile becomes the primary distribution target, console delivery becomes a requirement, or profiling shows browser memory/rendering limits prevent the required scope. Assess platform support and export constraints then; a native-primary decision is not a promise of equivalent web support. Revisit the renderer on measured browser incompatibility or demonstrated limits, not speculative scale. **WebGPU is deferred**; WebGL2 is the prototype baseline. This decision does **not** choose a source-code license; review dependency obligations separately when installing packages.

## ADR-002: deterministic domain

- Canonical tile ID is **`z * width + x`**, row-major. Coordinates derive from ID; renderer chunk, vertex or draw indices are not tile IDs.
- Validate dimensions as integers **8–256** and seed as **`^[A-Za-z0-9_-]{1,64}$`** at the domain boundary. Reject bad values before allocation or generation.
- **Generator version 5, inherited land generation:** hash the ASCII seed with unsigned 32-bit **FNV-1a**, then generate randomness with **Mulberry32**. Separated continent forms live in world space, where hex rows lie `√3/2` apart, and are sized by tile count. V4 introduced warped sampling and seeded curved inlets in sufficiently large continents; their mouths connect to the ocean and their rounded heads penetrate inland. V5 preserves that complete land/water mask, stepped elevation, trees and PRNG progression. Regression fingerprints captured before adding bathymetry cover 32², 64 × 48 and 256² worlds; existing multi-seed continent/bay tests remain. PRNG state is explicit, never a global singleton or `Math.random()`.
- **Canonical bathymetry (G1/#53):** after the land pass, a multi-source hex BFS computes integer distance from land in linear time. Seeded broad shelf-width variation, elongated offshore bank lobes and fine perturbation turn that distance field into irregular depth regions, not constant-distance rings. They use stable hashes of the inherited final RNG state without consuming another transition. Every water `Tile` requires one `waterDepth` value (`shallow`, `shoal`, `shelf`, `deep`); land has none. Tiles and the map remain immutable. The complete field is generated once, independent of fog, viewport and voxel density. All four tiers, mixed shallow/deeper classes at the same coastal distance, broad connected upper-tier extensions at least three hex steps offshore and retained deep water are tested across three seeds and 32², 64 × 48 and 128² maps. Each fixture has at least two such offshore hexes with at least three shallow neighbours and a deep-water share between 25% and 95% of its water. No route is repaired to connect islands. Final start/beacon reachability and fairness belong to P2/P3a.
- **Compatibility:** `mapHash` includes each canonical water depth, so a depth-only edit is detectable. Generator-v5 complete-map fingerprints intentionally differ; v3/v4 packages are rejected and readable saves remain byte-for-byte stored/listed, with only their own auto-resume pointer cleared. At G1, rules stayed v4 and the turn envelope stayed unchanged. P2 subsequently raises rules to v5 and adds a deterministic scenario descriptor; water remains impassable, starts still share a connected landmass, and boats/separate playable island starts remain deferred. Further changes to canonical depths require a generator boundary; adding water movement requires a rules boundary.
- **P2 shared-landmass scenario (#36):** rules v5 adds scenario-defined starting positions, three reserved public beacon tiles and production of later founders; generator v5 is unchanged. Scenario v1 deterministically selects starts and beacons from the largest connected landmass, validates weighted travel-turn fairness and reserved city-site capacity, and rejects unsuitable maps without repairing them. A rules-v5 match package carries only the scenario version and the two independent tribe IDs; seed, generator and scenario version reconstruct the placement, while the complete scenario is included in `stateHash`. This compact selection keeps long turn codes bounded. Existing rules-v4 archives remain readable and stored, but are never replayed under v5. Separate home/beacon islands and water movement remain P3a.
- Use stable row-major generation. Future entity IDs, command sequence numbers, neighbor order, and tie-breakers must be explicit; hex neighbour order is **east, south-east, south-west, west, north-west, north-east** (`HEX_DIRECTIONS` in `src/game/hex.ts`). Avoid relying on unordered collections or callback completion order.
- Keep authoritative arithmetic integer-based where practical. Never use frame delta, wall time, DOM state, or Babylon transforms to resolve gameplay.
- Unit tests must verify fixed fixtures, repeatability, PRNG state transitions, rectangular-map IDs, bounds, and invalid inputs.

**Command resolution:** rules v1 established movement and turns, v2 founding/economy, v3 hex neighbours/distances and faction city names, and v4 extended movement to all current unit types. **Rules v5** adds validated scenario placements, beacon reservation during city founding, and later founders as a city production choice when another city slot remains. Scouts retain 4 movement points; founders, guards and workers have 2. Each unit has an independent budget; all incoming-faction budgets reset on turn start. All own units and cities provide radius-2 sight; movement reveals its route, then visibility is recomputed from their union, returning only changed fog IDs. `applyCommand` rejects illegal faction, sequence, occupancy or budget with the identical state and a reason. Accepted immutable snapshots and logs remain deterministic and consume no RNG. Cities resolve in founding order before control advances, with round increments on wrap. Readable older-rule saves remain stored and listed; only their auto-resume pointer is cleared. Shape parsing preserves the package version; replay rejects unsupported rules before generating the world.

`findPath` uses A* with the hex distance as heuristic (admissible, since every step costs at least 1) and `movementRange` uses Dijkstra, sharing a binary min-heap. Equal priorities preserve insertion order, neighbors follow the fixed hex direction order, and equal-cost rediscoveries retain the first parent. Searches stop at the current integer movement budget and cannot traverse uncharted terrain, water or occupied tiles. The UI submits commands and displays domain outcomes rather than independently resolving rules.

## ADR-003: data and persistence

Terrain/resource definitions are typed, data-driven records with stable symbolic IDs. City yields, founding constraints and production items follow the same approach; their effects live in `src/game`, separate from HUD presentation. Future research, policy, and faction definitions should follow this pattern. Validate references and constraints on loading; keep presentation metadata separate from authoritative effects.

**Future saves/replays—not prototype features:** use an envelope carrying schema, generator, rules, content, and RNG algorithm versions, map dimensions/seed, canonical entity IDs, explicit RNG state, turn/phase, and command-log version. Saves contain authoritative state; replay starts from the recorded initial state and ordered commands. Validate shape, bounds, unique IDs, references, versions, and size limits before accepting either. Reject unsupported versions clearly; migrations must be explicit and tested. Do not serialize Babylon meshes or assume a seed alone reconstructs a progressed game. Verify state hashes at checkpoints to detect replay divergence. The **match package** of ADR-005 is the first, deliberately narrow use of this idea: a versioned, validated command log replayed from a seed with two checksums. It does not carry content or RNG-algorithm versions yet, because no command consumes randomness.

## ADR-004: map and rendering

- **Hex grid, six-direction movement** (rules v4, generator v5). Tiles are pointy-top hexagons in **odd-r offset** layout: odd rows shift half a tile east, so the canonical row-major ID and rectangular storage are unchanged. Neighbours, distances, axial conversion and point-to-hex rounding live in the pure module `src/game/hex.ts`. Hexes give six equally long steps and no corner ambiguity, which suits territory, movement ranges and the board-game reading of the approved concept (`docs/concept-hex-voxel.jpg`). The square grid was replaced in rules v3 with explicit user approval; older-rule matches require a compatible version.
- World axes: **x east, z south, y up**. Tile centres lie one unit apart: `(x + ½·(z odd), z·√3/2)`. One consistent tile scale and origin for generation, rendering, camera bounds, and picking.
- Current renderer: **hex fields built from cubic voxels, in 66 × 66-column chunks**, one mesh per chunk, not one mesh per tile. The pure module `src/rendering/voxels.ts` builds a voxel volume from the domain map, with **16 voxels per tile** (centre to centre) when both dimensions are at most 32, 8 up to 64, 4 up to 128 and 2 above. Powers of two keep voxel coordinates exact and cap the columns at 520 per axis. Every voxel column belongs to the hex containing its centre (`columnTile`), so each hex is a stepped hexagon of square columns; the 32² showcase has 520 × 449 columns in 8 × 7 chunks. Land stacks a stratified soil base, banded dirt or rock cliffs, a grass, sand or rock surface, low connected upland terraces, and up to five trees at fixed screen-aligned spots (back row first, so the centre and front stay free for units), plus sparse tufts, flowers and stones stamped deterministically from the map seed. Water contains a stepped solid seabed and coastal rocks, either submerged or breaking through the translucent cap, with opaque blue walls closing the diorama cut edges. Whole trunk footprints stay on their charted tile and exclude sandbanks; crowns can overhang the coast. Uncharted columns are fog from top to bottom and cannot outline unknown terrain. A greedy mesher emits visible faces with palette colours and per-corner ambient occlusion; faces merge only when their occlusion is uniform. Solid faces bordering transparent water remain visible; transparent water neither hides those faces nor occludes their ambient light. Stamps only fill empty voxels and each chunk meshes a one-voxel apron, so chunk borders are identical from both sides. A dedicated `polarisFaceFlag` float vertex attribute marks faces as fog (0), decoration (0.5), ground (1), water floor (1.125), submerged solid (1.5), water surface (2) or shoreline surface (2.25); the water cap's blending is controlled by its material alpha, not the flag. The module holds no Babylon objects; Node tests cover winding, chunk-border equivalence, hex column ownership, fog leaks, picking and vertex budgets.
- **Viewport detail on maps up to 256².** The map-size densities above are the overview baseline, not a permanent cap. `detail.ts` selects 2/4/8/16 from the camera's world-space footprint, with height/shadow clearance and upgrade hysteresis. Higher densities allocate only a padded, chunk-aligned window: fewer than 602,176 resident columns and at most 144 chunks, independent of total map area. The whole visible window changes resolution together, so no mixed-LOD seam or mismatched water plane crosses the view. Existing global chunk keys retain meshes during pan; departing chunks and replaced column textures are disposed. Reset restores the overview. The detailed 32² showcase remains unchanged.
- **Global lattice, local storage.** Window offsets are integer multiples of 66 columns. CPU noise, tree/fruit grain and shader material cells include those offsets; moving the window cannot move the patterns. Column sampling outside resident storage still reads the canonical map and viewer knowledge, so coastal influence, apron AO and overhanging decorations agree with full-world meshing. Only the active window has geometry/state-column storage; picking uses its bounds, while figure/plate projections can sample terrain outside it without allocating extra grids. Fog/site changes invalidate intersecting resident chunks, and future chunks use current knowledge/sites. Unit tests compare byte-identical full-grid and cropped chunk geometry. The camera footprint includes the complete three-unit decoration-height envelope.
- **Fine showcase, bounded larger maps.** Tree crowns/trunks, settlement stamps and coastal reach scale with voxel resolution, retaining world-space proportions; detail probability is reduced per column to avoid multiplying tufts. Domain generation, IDs, rules, visibility, PRNG and save compatibility do not change. Voxel-rounded heights may step during a density switch; figures, picking and markers are repositioned against the same active sampler. Meshing remains synchronous, not background streaming; first entry and newly exposed chunks can pause, so native-device frame-rate validation remains open. `residentColumns` reports allocated columns and `streamedChunks` counts newly built camera-detail chunks separately from fog/site remeshing.
- **Low connected highlands, not per-hex pillars.** Grassland and hills share a 0.65 base height; each domain elevation step adds 0.125 world units before voxel rounding. Detailed scales 16 and 8 therefore put elevations 1–4 at **0.625, 0.75, 0.875 and 1**, above water at 0.25. Remove the former hills-only height jump and individual terraced hex domes. At scale 4 the levels merge to 0.75/1; at scale 2 all dry land is 1 above water at 0.5. Coarse detail must not invent extra height just to separate every elevation. Hill identity, domain elevation, movement and yields remain; shared actual-column sampling keeps picking, figures and levelled settlements aligned. Grey resource outcrops provide localized relief instead of a mountain on every hill tile.
- Cities are drawn as **voxel settlements** inside the terrain chunks, not as extra meshes. The renderer receives a settlement view per city (tile, population, storehouse, faction) and stores a one-byte code per tile in `VoxelWorld.sites`. A settled tile is levelled to its pickable surface and loses its trees and resource occurrence; it shows a stone keep with a faction banner, one to three terracotta-roofed houses by population, and a thatched storehouse once built, all inside the hex's own columns. Trees on the back row of the hexes in front of a settlement are left out, so the town stays visible. At 4 and 2 voxels per tile the layout shrinks to one house (plus a small keep at 4). Volume height reserves the larger of the tree and settlement bounds at each scale, so smaller trees cannot clip keep banners. Changing a code remeshes only the chunks around that tile. The expedition passes the viewer's own cities and rival cities only while their tile is visible; remembered last-known cities are not drawn yet.
- `world.ts` uploads each chunk as one `Mesh` and geometry, with opaque indices first and transparent water indices last (`waterIndexCount`). Two submeshes share a `MultiMaterial` containing terrain and water `StandardMaterial`s; both use the same material plugin and state textures, with a shader define separating their cached terrain and water variants. Water adds at most one colour pass per water-bearing chunk, not per voxel or tile. The plugin adds per-voxel colour grain on solids, explored dimming, the reachable-range tint and territory tint, plus flat unlit fog. It reads two small state textures: a **width × height tile-state texture** (R explored, G reachable, B territory, A charted) and a **column texture** holding the owning tile's state for every voxel column. Ordinary hex hairlines appear on upward-facing land and water-cap surfaces, never on the submerged floor. Reachable and territory tints/borders remain on land. The grid fades further when zoomed out; selection, reachable outline and territory border remain distinct. The territory byte (`territoryCode`) carries the owner plus one bit per hex edge where the territory ends. Explored dimming, ranges and borders update in place; newly charted terrain remeshes only affected chunks, including coastal decoration and trees whose roots/crowns depend on a changing land sand pocket.
- **Four canonical underwater terraces, not density-driven microsteps.** The maintainer's comparison rejected both the former patterned plane and the later 15 fine seabed heights. The generator's shallow, shoal, shelf and deep hexes map to world-space floors **0.125, -0.125, -0.375 and -0.625**, beneath the level water surface **0.25**. Both scales 16 and 8 retain these four terraces. Scale 4 merges unrepresentable levels into three heights (0, -0.25, -0.5); scale 2 retains its single -0.5 floor and omits rocks, but keeps all four cap-colour classes. Sparse seeded outcrops remain separate from the main terrace count and never change a hex's depth. The seabed shows pale sand in the shallows, patchy sand/stone on the shoal, muted stone at the shelf and a deep blue floor. Every seabed material uses the water-floor face flag, never the land grid. Real top and side faces remain visible through a level alpha-0.4 cap; colours support rather than replace geometry. Terrain and water plugins retain distinct shader-cache defines; cut walls remain opaque blue. A charted water hex's depth is observed terrain, even when adjacent land is unknown; revealing that land cannot reclassify the water or change its floor. Unknown tiles contain only opaque fog, not seabed, rocks, picks or labels. Only charted neighbours influence coastal rocks/highlights and land beaches. Tests verify exact floor heights, stable known depths across fog/LOD, hidden-neighbour independence, cropped-window equivalence, cap coverage, opaque/transparent separation and coastal-decoration invalidation.
- **G1 data versus planned P3a navigation:** charted-water hover/selection names the same canonical class used by geometry and cap colour. Ordinary boats are planned to use shallow/shoal; shelf/deep require deep-water capability. Offshore shoals remain water, not new land or disembarkation sites; they are distinct from sand pockets within existing land. Movement still rejects every water tier. P3a adds navigation/scenario validation and must test start/beacon reachability and deep-water-only expansion islands rather than assuming G1 guarantees them.
- **Compact coastal rocks, below and above water.** Seeded, quarter-turned groups combine three uneven voxel lobes within roughly one hex of charted land, not in open ocean or fish occurrences. Fully submerged groups rise at most 0.375 world units from the local floor, avoiding tall needle-like pillars; some groups on shallow/shoal floors rise 0.125–0.25 above water. Underwater portions use the submerged-rock palette and exposed tops are grey. Solid columns reaching the cap replace it in their footprint: cap area plus exposed-rock area must exactly cover water-owned columns, without overlap. Emerged columns participate in the shared height sampler and DDA picker, but remain canonical **water** tiles with unchanged movement rules. Hiding nearby land removes its rocks and shoreline highlights, not the already-charted water's canonical depth.
- **Smaller trees and presentation resources.** Detailed trees are at most 0.75 world units high, down from 1.125, with narrower crowns; scale 4 keeps at most two simplified trees and scale 2 one central canopy voxel. `resourceAt` hashes the seed and tile coordinates to assign stone deposits to hills, apple groves to grassland and fish shoals to water. It does not mutate `Tile`, advance the simulation RNG or add yields, harvesting, occupancy or movement rules. Land resource sites remain dry instead of being lowered into sandbanks; occurrence identity stays stable as neighbouring coasts are charted. Deposits replace normal trees with overlapping grey blocks and optional rubble, varying their mirroring, offsets, widths, heights and chipped shoulders. Broad flat caps at several heights avoid identical narrow towers; detailed peaks rise at most 0.625 world units above the low ground, and scale 4 and finer keep the tile-centre column clear for units. Groves stamp up to three round trees with real red fruit voxels at detailed scales. Cities suppress their occurrences.
- **Bounded resource annotations.** `resources.ts` supplies shared names, height offsets and original inline SVG glyphs; these are projected HTML annotations in the existing city-plate layer, not terrain textures, billboards or new WebGL meshes. The renderer's public lookup, hover/selection text and glyphs expose only charted occurrences. Remembered glyphs use opacity 0.58. Candidate iteration is bounded to the camera footprint; only the nearest 128 on-screen markers may have DOM nodes, and none are kept below 40 CSS pixels per world unit. Pan/zoom/resize and exploration/site changes reposition or remove them; regeneration and disposal release them. Resource glyphs remain non-interactive so picking beneath them still targets terrain; unit and city buttons in the same layer handle direct orders. The inspector explicitly says harvesting is unavailable.
- **Irregular sandbanks cut existing land, not new water-tile islands.** Seeded broad and fine noise varies a bank's width up to about 0.9 world units along the charted coast. Distance to **charted water**, using the same conservative bounds and exact column-distance sampler as coastal decoration, lowers patches of grassland and cliff to sandy tops at 0.375 and 0.5. Their sides are sand above the stratified foundation; broad pockets alternate with intact cliffs instead of painting a narrow rim on the old top. Coarse scale 4 merges the two tops; scale 2 omits banks. No normal tree trunk footprint may sit on sand, and banks get sparse stones rather than tufts. Settlement levelling and dry land-resource sites take precedence. Land/water identity, domain elevation, movement and PRNG remain unchanged. Unit tests require irregular widths, real lowered geometry covering more than one world square unit, supported coastal trunks, no influence from unseen water and level settlements. A browser check measures a visible sandy area around a lowered tile centre and selects its unchanged canonical land ID.
- Lighting is a hemispheric fill and a directional sun with one 1024² PCF shadow map. The shadow map uses a 16-bit single-channel colour target plus 32-bit depth, about 6 MiB, fixed and independent of map size. Opaque terrain and submerged solids cast shadows; the transparent cap does not. Apart from throttled water glints, the map redraws only after changes once shaders are ready. Generator-v5 production diagnostics at `2bd9da6` report chunk vertex/index buffers of about **21.0 MiB / 439,972 vertices** for the fine 32² showcase, **25.8 MiB / 541,800** at 64² and **17.6 MiB / 370,080** at 256², excluding shadows, state textures and CPU copies. Canonical depth boundaries split some greedy quads but add no meshes; coarse terrain still merges elevations instead of growing tall columns. All three fixtures have **56 chunks + 2 hex markers = 58 meshes, 6 materials** (terrain, water, figures, rival ring, hover, selection), plus the shared `MultiMaterial`. Resource glyphs add no WebGL objects. Geometry counts remain equal to mesh counts. All three sizes must stay below the existing **900k vertex ceiling**.
- **Surface material shades supplement geometry.** The material plugin combines two smooth procedural patch fields with per-cell grain, quantizes them into five tones and applies material-specific RGB multipliers to upward-facing land and water-cap faces. This replaces the overly uniform surface reading without changing the accepted seabed. Cells are anchored in global voxel-column space, continuous across hex and chunk boundaries: one voxel on ground, 2 by 2 voxels on water to avoid fine visual noise. Derivative-based filtering fades their contrast as they become subpixel, and the shoreline receives only 35% of the contrast. Existing solid grain, baked occlusion, lighting and real underwater relief remain; decorations and opaque fog are excluded, and territory/reachable overlays apply afterward. No image texture, additional geometry, state texture, animation or rules/PRNG change is introduced. Browser framebuffer tests check water/grass tonal spread, flat colour inside cells, camera-independent world anchoring and unchanged vertex/buffer counts. The grass test also checks the interquartile colour range so isolated tufts or stones cannot masquerade as surface shading.
- **Rendering on demand, with throttled water glints.** Camera, markers, map, fog, figures and resize call `invalidate()`. The only animation is sparse sun glints on visible water-cap faces: a world-space cell hash chooses brief flashes, grouped by a drifting low-frequency field. Peak sun-colour blending is capped at 0.35 rather than 0.85; per-cycle selection probability is `0.003 + 0.04 * gust`, reducing bright distractions while preserving the water colours and seabed. A time uniform updates on idle frames at least 80 ms apart; no geometry, simulation RNG or shadow refresh changes. Glint cells adapt from 1/16 to 1/4 world units to avoid subpixel noise. Reduced motion, far overviews and absence of resident visible water disable the animation; remembered water never glints. The media-query listener is removed on disposal. Shader compilation still requests frames until ready. Diagnostics report `waterGlint` strength and cumulative `renderedFrames`.
- **Direct selection and static availability.** Own unit figures have projected transparent button targets and static CSS halos, not replacement sprites or per-object WebGL effects. Their targets scale down with the view to avoid swallowing neighbouring destination taps. Own city name plates are buttons. Pointer capture shares the canvas's five-pixel drag threshold and pinch handling; keyboard activation is supported. Unit selection submits the domain-computed affordable range; destination taps issue `move` immediately. City selection opens its production controls. Only units with a legal move and cities with empty queues glow, and only while the viewer may act. Switching selection, moving, queuing, turn changes, fog, camera detail and regeneration refresh or remove targets and glows. Resource annotations remain non-interactive.
- **Framebuffer-calibrated palette.** The approved concept calls for yellow-green grass, cyan shallows and saturated deep blue, pale sand, warm grey stone, olive/forest foliage and terracotta roofs. Calibrate the final rendered colour, not raw palette RGB: vertex occlusion, lighting, material tones and alpha blending all affect it. Unobstructed, resource-free 32² browser samples target concept medians `[151,171,60]` for grass and `[11,117,170]` for deep water, with an eight-byte per-channel tolerance. Shadowed coasts and different compositions are not pixel-identical illustration samples. The cap uses distinct shallow/shoal/shelf/deep palette kinds chosen from the existing charted-only coastal classification. They all retain the water-surface face role, material and level; a single dark blue alpha-0.4 cap could not also reproduce bright cyan shallows. Coastal caps disappear when their source coast is uncharted and are omitted at scale 2. Water tone contrast compensates for the darker deep-blue base without changing its mean.
- **Thin, antialiased frames on land and water.** For each hex-edge direction, compute the Euclidean screen-pixel footprint from derivatives of continuous world coordinates before branching; never differentiate rounded hex-local coordinates. A coverage hairline replaces the old broad grid smoothstep; both land and water profiles must stay within 0.75–1.5 framebuffer pixels at two inspection zoom levels, without a broad halo. Water lines are now intentionally visible on the cap, superseding the earlier suppression; never put them on the seabed. A negative control disabling water lines measured only 0.58 luminance contrast and failed the required >8; land retains >12. The earlier broad shader measured 3.5 pixels and failed. Reachable bands are 0.012 world units wide; territory bands 0.032, their dark seam 0.043 and restrained glow 0.12. These use the same pixel-aware coverage but keep their faction/interaction identity. Hover rings span 0.95–0.98 of the hex corner radius, selection 0.92–0.98 and rival dashes 0.9–0.97. Profiles cover all three edge orientations; gameplay tests retain scout readability and selection behavior.
- **Units and cities.** Units are small voxel figures (`src/rendering/figures.ts`, 1/24-unit voxels, cached per kind and faction) standing on the visible voxel under their feet; several units on one hex stand side by side. Rival units also get a dashed red hex ring. Each visible city gets an HTML name plate with its population above the keep, positioned from the camera matrices after every camera change.
- Picking does not ray-cast meshes or cache a flat per-tile height. `pickTile` walks the camera ray through voxel columns (2D DDA), sampling the same actual ground heights as meshing and figure placement, including lowered sandbanks, hill mounds and emerged coastal rocks. Unseen fog and water without a possible coastal rock use a flat fast path; other water samples the cap or rock, never the submerged floor. The first intersected column returns its canonical hex ID; tree/deposit decorations and resource glyphs never intercept picks and identity never derives from draw order. Tests compare against brute-force intersections and show water becoming visible through a lowered bank, then hidden again by a levelled settlement. Markers, rival rings, diagnostic projection and city labels also use the actual centre height. Existing selection markers are repositioned when exploration or settlement changes reshape their coast.
- Separate selection overlays from terrain chunks; hex-ring markers and unit figures render in a later rendering group so trees cannot hide them.
- Fixed orthographic camera at **yaw 45°, pitch `atan(1/sqrt(2))` (35.264°)**, no rotation. This replaces the former 60°/42° view at the maintainer's request: equal cube-axis lengths and symmetric 30° screen slopes follow the approved concept's isometric construction. The illustration has no camera metadata and contains local projection variation, so these values are a calibrated consistent projection, not a claim that one exact source camera was recovered. `src/rendering/view.ts` supplies the shared basis for camera/pan/framing, tree placement and figure facing; picking tests use the same view. Browser tests independently measure actual projected axis lengths and slopes. Movement buttons keep their six relative directions, but hex edges are no longer forced vertical/horizontal on screen; the lower view can correctly hide low terrain behind higher foreground terrain. Pan target clamps to the hex centres (`0..width-½` in x, `0..(height-1)·√3/2` in z), with no outside padding. Zoom half-height clamps from 3 world units to an aspect-correct whole-map fit with 2 units of framing margin. Resize preserves the relative zoom. Ray intersection/pick results go through the mapping adapter, then domain bounds validation.
- Dispose old chunk meshes, both state textures, figures, name plates, listeners and selection on regeneration. Clear stale picks and selection before showing a replacement map.
- Detect missing WebGL2 and display a useful fallback message rather than an empty canvas.

### Future incremental work and simulation costs

Implemented fog is a faction-owned sparse immutable record of explored/visible tile IDs; absent entries are unseen. Terrain is immutable, so the map itself is the remembered terrain source. Moving copies the discovered record, processes old/new/traveled sight regions (not every map tile) and returns only changed visibility IDs. End-turn and camera motion do not alter fog. Mutable last-known terrain and enemy-unit hiding remain brief 11 work.

Unseen tiles are meshed as one flat slab at a uniform fog height and colour. They have no terrain-dependent height, silhouette, shadow, occlusion, trees, water-depth label or picking result. Only charted neighbours shape beaches, shoreline highlights and coastal rocks, and trees grow only from charted tiles. Known water retains its own canonical depth regardless of those neighbours; the renderer never reconstructs depth from hidden terrain. Explored dimming, reachable tiles and territory borders come from the state textures, updated in place, so remembering terrain, showing ranges and moving borders never remesh. When tiles become charted or gain a settlement, only chunks within tree or coastal-decoration reach are remeshed (`affectedChunks`), in place; mesh and geometry counts stay constant. Full mode transitions and regeneration initialize all tiles. Unit figures and rival rings are separate non-pickable meshes rendered above the terrain and are disposed on every exploration update, on leaving the expedition and on regeneration. No per-tile meshes or per-frame visibility computations are added.

Pathfinding should start with deterministic A* for a single destination and Dijkstra for movement ranges. On a hex grid every tile has at most six edges, so edges scale with tile count; heap-based searches can approach O(V log V) and O(V) memory. Repeating a full search for every unit/candidate can dominate AI turns. Bound AI candidate sets and search counts, reuse valid results with explicit terrain/occupancy invalidation, and measure expanded nodes and per-turn work. Defer Web Workers until profiling shows main-thread stalls justify serialization and coordination costs. If introduced, use immutable inputs, explicit RNG state and ordered results; worker scheduling must not alter outcomes. This refers to browser threads, not gameplay worker units.

## ADR-005: serverless play by messenger

**Decision:** two players exchange finished turns as text through any messenger, e-mail or file. A turn message is a **match package**: the complete ordered command log of the match so far plus what is needed to rebuild the world, never a snapshot of state.

```text
MatchPackage { format, matchId, rules, generator, seed, width, height, factions, scenario?, commands[], mapHash, stateHash }
```

- **Replay, not state.** The receiver regenerates the map from seed and generator version; under rules v5 it also rebuilds the canonical scenario from scenario version and two tribe IDs, then replays every command through `applyCommand`. This relies on ADR-002: integer arithmetic, explicit tie-breaks, no wall time and no randomness in commands. `mapHash` (hash of the generated tiles) proves both devices built the same world; `stateHash` (canonical hash of the replayed state, including the complete scenario and fog) proves they reached the same position. A mismatch is refused with a reason and never half-applied.
- **Turn discipline.** `MATCH_FACTIONS` fixes the player order, not the tribe choice: player 1 creates the match and moves first; each player independently chooses a tribe, including mirror matches. The scenario envelope carries the version and tribe pair; the deterministic starts/beacons are derived rather than repeated in every turn. A received package must end with `end-turn`, extend the local log of the same `matchId` (the shared prefix must be identical) and contain no orders for the receiver's own player-specific faction. Equal or shorter logs are reported as already known. Duplicates, reordering and lost messages are therefore harmless: the newest package supersedes everything before it, and an opponent's message can also start a match on a device that has never seen it.
- **Several matches.** The receiver reads the `matchId` before replaying and checks the package against that match's saved log, whichever match is on screen; an unknown `matchId` starts a new match. So any number of matches run side by side without the player sorting messages. The list of saved matches reads only the package shape and counts `end-turn` orders for round and active side (`matchProgress`); the full replay happens when a match is opened.
- **Untrusted input.** Packages are pasted text: caps on text (1.5 M characters) and decompressed JSON (1 MB), at most 10,000 orders, strict shape and identifier checks before the world is allocated, and the usual seed/dimension contract. Compact orders are re-validated by the normal rules during replay.
- **Outgoing boundary.** `applyMatchCommand` applies the same 10,000-order transport bound before accepting local messenger orders, reserving the last slot for `end-turn`. Rejection leaves state, log and RNG untouched. `applyCommand` and replay remain deterministic under rules v5. Exhausting transport capacity is not a game result. Separate `parseStoredMatch` validates local archive shape for retention, including over-limit logs; it is never used to bypass `parseMatch`/`openMatch` on incoming turns.
- **Encoding and compatibility.** `polaris1z.<base64url(deflate-raw(JSON))>` with `CompressionStream`, falling back to `polaris1j.<base64url(JSON)>`. Format 1's rules-v5 package requires the compact scenario selection; the original seed and selection deterministically reconstruct all placements, avoiding an unnecessarily large turn payload. Older rules-v4 records without this field remain structurally readable and stored, but are rejected before replay with an incompatibility reason. The decoder also accepts a link (`#turn=` fragment), a chat message around a code, or the JSON of a saved file. The fragment never reaches a web server.
- **Persistence.** Each match is stored as a package with the player's faction and an optional local name under its own `localStorage` key `polaris.matches.v1.<matchId>`; `polaris.current-match.v1` names the match that reopens after a reload. A match is replayed and verified when it is opened. Structurally readable records with a matching ID, valid faction and incompatible rules/generator or over-limit history are retained byte-for-byte, with a visible reason; only their own auto-resume pointer is cleared. They remain listed without replay or automatic conversion, and incoming turns may not overwrite them. Damaged or otherwise invalid records are still discarded with a visible reason; removal failures are reported rather than claimed as successful. The single match of earlier versions (`polaris.match.v1`) is migrated on start, keeping its original record if copying fails. The outbox is derived from state and faction instead of stored, so a reload offers the identical link.
- **Failed writes.** Storage operations return explicit success/failure results. The composition root sets auto-resume only after the record is saved and reports pointer/removal/migration failures separately. Deletion clears only the match's own auto-resume pointer before removing its record, so failed pointer cleanup leaves the save recoverable. A persistent storage-warning line is independent of transient copy/share notices. Shelving and cross-match imports, including the known/older-message path, retry saving and retain the current in-memory match on failure; only explicit Leave discards it. A successfully saved record remains usable from Your matches even if setting its auto-resume pointer fails. Without a successful save, browser reload/closure can still lose progress: keep the page open and export/send a completed turn first. This prevents a false saved confirmation without turning storage into an authoritative game rule or reverting an accepted in-memory order.
- **Presentation.** `main.ts` remains the composition root. The viewer faction decides what is rendered (own fog, own scout, own reachable tiles) and whether orders are accepted; `src/game` knows nothing about devices or messengers.

| Alternative | Why not now |
| --- | --- |
| Hot-seat on one device | Two people cannot play remotely; rejected by the project owner |
| WebRTC or Bluetooth | Needs a live peer and a signalling exchange that is itself a copy-and-paste step; NAT and browser support add complexity |
| Relay or lobby server | Adds hosting, accounts, abuse handling and cost before the rules justify it; remains the path for secrets, simultaneous turns and notifications |

**Consequences and risks**

- No anti-cheat: both devices know everything, fog is presentation, checksums only detect accidents. Both players need the same game, rules and generator version; a mismatch is reported.
- The generator uses `Math.sin`, `Math.cos`, `Math.hypot` and `Math.sqrt`, whose last bits are not guaranteed identical across JavaScript engines (for example Chromium and Safari). Tile classification would only flip on a near-tie, and `mapHash` turns any such divergence into an explicit refusal at join time instead of a silent desync. Cross-engine play should still be tested on real devices; a table- or integer-based replacement needs a generator version bump and new fixtures.
- Links grow with the log. A file export is the fallback for chats that cut messages; delta packages (only the new orders plus a checksum of the shared prefix) are the next optimization if logs get long.
- Revisit with a server when hidden information, more than two players, asynchronous notifications or ranked play become requirements. The command log and checksums carry over unchanged.

## Benchmark protocol

**Initial evidence:** the first benchmark here will be a shorter software-rendered runner sample, not the full protocol below. Report its actual duration, sample count, software renderer, environment and limitations alongside results. Do not extrapolate it to hardware-rendered desktop/mobile performance, sustained frame rates, or leak-free operation. No numbers below are measurements.

**Future full protocol:** use the **32 × 32 showcase** and **256 × 256 stress fixture**, with fixed published seeds and generator version. Record browser/version, OS, CPU/GPU, RAM, viewport, device-pixel ratio, power mode, build mode, and commit. Test a production build on named desktop and mobile-class reference devices; runner results are not a device baseline.

After warm-up, perform five regenerations and a repeatable 30-second pan/zoom/pick path. Report median and worst generation-to-interactive time, p50/p95 frame duration, pick latency, draw calls, instance counts, and available memory indicators. Capture cold-load separately. Repeat regeneration 20 times to check retained resources; distinguish noisy browser memory indicators from verified leaks.
