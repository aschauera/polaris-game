# Polaris: architecture

## Scope and boundaries

Browser-first **strict TypeScript + Vite + Babylon.js WebGL2**, in a single package. The atlas, the first scout-exploration slice and a serverless two-player turn exchange (ADR-005) are implemented, not the full first-playable match. Pure `src/game` owns generation, commands, pathfinding, faction fog and the match package (replay plus checksums). Use **Vitest in Node** for domain tests and **Playwright** for browser behavior.

| Directory | Responsibility | Must not contain |
| --- | --- | --- |
| `src/game` | Definitions, seeded generation, immutable expedition state, commands, movement/fog, match packages (replay log and checksums); later saves/AI | DOM, Babylon objects, wall-clock time, renderer state |
| `src/exchange` | Turn codes (compress, encode, decode links/files) and the browser-storage adapter for a running match | Game rules, Babylon objects; storage is injected, never reached through globals |
| `src/rendering` | Babylon scene, pure voxel construction/meshing (`voxels.ts`), camera, heightfield picking adapter | Authoritative gameplay rules or independent tile state |
| `src/ui` | Inputs, validation feedback, inspector, HUD, messenger panel | Simulation logic or direct mutation of domain state |

Dependencies point toward `src/game`. A small composition entry point wires adapters together. Rendering and UI consume domain snapshots/events and submit intents; neither determines authoritative outcomes.

## ADR-001: browser stack

**Decision:** strict TypeScript, Vite, Babylon.js, WebGL2, one package.

| Alternative | Tradeoff and reason not selected |
| --- | --- |
| Godot native | Strong editor and native pipeline. Current Godot 4 C# projects cannot export to web; web export requires the Compatibility renderer and WebGL2, not Forward+/Mobile rendering parity. Those constraints favor the TypeScript browser stack here |
| Three.js renderer | Flexible, smaller rendering abstraction; more camera, picking, batching, and tooling assembly than Babylon for this prototype |
| Unity | Mature tooling, but heavier browser delivery and proprietary terms require a current legal/commercial terms review before any adoption |
| Bevy/Rust | Attractive ECS and native performance; Rust/WASM integration and browser tooling add complexity before gameplay needs justify it |

Revisit Godot if native desktop/mobile becomes the primary distribution target, console delivery becomes a requirement, or profiling shows browser memory/rendering limits prevent the required scope. Assess platform support and export constraints then; a native-primary decision is not a promise of equivalent web support. Revisit the renderer on measured browser incompatibility or demonstrated limits, not speculative scale. **WebGPU is deferred**; WebGL2 is the prototype baseline. This decision does **not** choose a source-code license; review dependency obligations separately when installing packages.

## ADR-002: deterministic domain

- Canonical tile ID is **`z * width + x`**, row-major. Coordinates derive from ID; renderer chunk, vertex or draw indices are not tile IDs.
- Validate dimensions as integers **8–256** and seed as **`^[A-Za-z0-9_-]{1,64}$`** at the domain boundary. Reject bad values before allocation or generation.
- **Generator version 3:** hash the ASCII seed with unsigned 32-bit **FNV-1a**, then generate randomness with **Mulberry32**. V3 places separated irregular continent forms in world space, where hex rows lie `√3/2` apart, sized by tile count so hex maps keep the land share of the earlier square maps; it then derives coast noise, stepped elevation and clustered trees. Preserve these algorithms and fixtures when refactoring; incompatible changes require a version bump. PRNG state is explicit, never a global singleton or `Math.random()`; future commands/saves must preserve it.
- Use stable row-major generation. Future entity IDs, command sequence numbers, neighbor order, and tie-breakers must be explicit; hex neighbour order is **east, south-east, south-west, west, north-west, north-east** (`HEX_DIRECTIONS` in `src/game/hex.ts`). Avoid relying on unordered collections or callback completion order.
- Keep authoritative arithmetic integer-based where practical. Never use frame delta, wall time, DOM state, or Babylon transforms to resolve gameplay.
- Unit tests must verify fixed fixtures, repeatability, PRNG state transitions, rectangular-map IDs, bounds, and invalid inputs.

**Command resolution:** rules version 1 established deterministic movement and turns; rules version 2 adds founding, city economy and production; rules version 3 moves the board to hexes (six neighbours, hex distances for sight, city spacing and claims) and names each city from its faction's fixed list in founding order. `applyCommand` validates faction, sequence and legality, rejecting with a reason and the identical state reference. Accepted orders return immutable snapshots, explicit affected tile IDs where rendering changes, and a user-facing outcome. The accepted-command log retains sequence order; no command consumes RNG. Movement resolves immediately. At end-turn, the active faction's cities resolve in founding order before control advances; incoming scout movement is restored and the round increments on wrap. No simultaneous resolution, AI or save format is introduced.

`findPath` uses A* with the hex distance as heuristic (admissible, since every step costs at least 1) and `movementRange` uses Dijkstra, sharing a binary min-heap. Equal priorities preserve insertion order, neighbors follow the fixed hex direction order, and equal-cost rediscoveries retain the first parent. Searches stop at the current integer movement budget and cannot traverse uncharted terrain, water or occupied tiles. The UI submits commands and displays domain outcomes rather than independently resolving rules.

## ADR-003: data and persistence

Terrain/resource definitions are typed, data-driven records with stable symbolic IDs. City yields, founding constraints and production items follow the same approach; their effects live in `src/game`, separate from HUD presentation. Future research, policy, and faction definitions should follow this pattern. Validate references and constraints on loading; keep presentation metadata separate from authoritative effects.

**Future saves/replays—not prototype features:** use an envelope carrying schema, generator, rules, content, and RNG algorithm versions, map dimensions/seed, canonical entity IDs, explicit RNG state, turn/phase, and command-log version. Saves contain authoritative state; replay starts from the recorded initial state and ordered commands. Validate shape, bounds, unique IDs, references, versions, and size limits before accepting either. Reject unsupported versions clearly; migrations must be explicit and tested. Do not serialize Babylon meshes or assume a seed alone reconstructs a progressed game. Verify state hashes at checkpoints to detect replay divergence. The **match package** of ADR-005 is the first, deliberately narrow use of this idea: a versioned, validated command log replayed from a seed with two checksums. It does not carry content or RNG-algorithm versions yet, because no command consumes randomness.

## ADR-004: map and rendering

- **Hex grid, six-direction movement** (rules v3, generator v3). Tiles are pointy-top hexagons in **odd-r offset** layout: odd rows shift half a tile east, so the canonical row-major ID and rectangular storage are unchanged. Neighbours, distances, axial conversion and point-to-hex rounding live in the pure module `src/game/hex.ts`. Hexes give six equally long steps and no corner ambiguity, which suits territory, movement ranges and the board-game reading of the approved concept (`docs/concept-hex-voxel.jpg`). The square grid was replaced with explicit user approval; matches and links of rules v2 no longer load.
- World axes: **x east, z south, y up**. Tile centres lie one unit apart: `(x + ½·(z odd), z·√3/2)`. One consistent tile scale and origin for generation, rendering, camera bounds, and picking.
- Current renderer: **hex fields built from cubic voxels, in 66 × 66-column chunks**, one mesh per chunk, not one mesh per tile. The pure module `src/rendering/voxels.ts` builds a voxel volume from the domain map, with **16 voxels per tile** (centre to centre) when both dimensions are at most 32, 8 up to 64, 4 up to 128 and 2 above. Powers of two keep voxel coordinates exact and cap the columns at 520 per axis. Every voxel column belongs to the hex containing its centre (`columnTile`), so each hex is a stepped hexagon of square columns; the 32² showcase now has 520 × 449 columns in 8 × 7 chunks. Land stacks a stratified soil base, banded dirt or rock cliffs, a grass, sand or rock surface, terraced hex mounds for hills, and up to five trees at fixed screen-aligned spots (back row first, so the centre and front stay free for units), plus sparse tufts, flowers and stones stamped deterministically from the map seed. Water contains a stepped solid seabed and submerged rock groups beneath a translucent cap, with opaque blue walls closing the diorama cut edges. Trees never cross into a neighbouring hex. Uncharted columns are fog from top to bottom and cannot outline unknown terrain. A greedy mesher emits visible faces with palette colours and per-corner ambient occlusion; faces merge only when their occlusion is uniform. Solid faces bordering transparent water remain visible; transparent water neither hides those faces nor occludes their ambient light. Stamps only fill empty voxels and each chunk meshes a one-voxel apron, so chunk borders are identical from both sides. A dedicated `polarisFaceFlag` float vertex attribute marks faces as fog (0), decoration (0.5), ground (1), water floor (1.125), submerged solid (1.5), water surface (2) or shoreline surface (2.25); the water cap's blending is controlled by its material alpha, not the flag. The module holds no Babylon objects; Node tests cover winding, chunk-border equivalence, hex column ownership, fog leaks, picking and vertex budgets.
- **Fine showcase, bounded larger maps.** The requested 16-voxel resolution doubles the samples along each hex edge and approximately quadruples its surface columns. Tree crowns/trunks, settlement stamps, hill relief and coastal reach scale with the voxel resolution so their world-space proportions are retained; detail probability is reduced per column to avoid four times as many tufts. The finer eastern house is inset one column to remain inside its hex at every row phase. Deep seabed foundations stay deep blue instead of exposing a stone band. A conservative charted-tile bounding check rejects open ocean before the exact column-distance search, reducing the original 32² meshing sample from about 3.1 s to 1.35 s without changing geometry counts. This predates the additional coastal cap colours and is a local CPU sample, not a hardware performance guarantee. Domain generation, rules and PRNG state are unchanged.
- Cities are drawn as **voxel settlements** inside the terrain chunks, not as extra meshes. The renderer receives a settlement view per city (tile, population, storehouse, faction) and stores a one-byte code per tile in `VoxelWorld.sites`. A settled tile is levelled to its pickable surface and loses its trees; it shows a stone keep with a faction banner, one to three terracotta-roofed houses by population, and a thatched storehouse once built, all inside the hex's own columns. Trees on the back row of the hexes in front of a settlement are left out, so the town stays visible. At 4 and 2 voxels per tile the layout shrinks to one house (plus a small keep at 4). Settlements fit within the tree height, so the layer budget is unchanged. Changing a code remeshes only the chunks around that tile. The expedition passes the viewer's own cities and rival cities only while their tile is visible; remembered last-known cities are not drawn yet.
- `world.ts` uploads each chunk as one `Mesh` and geometry, with opaque indices first and transparent water indices last (`waterIndexCount`). Two submeshes share a `MultiMaterial` containing terrain and water `StandardMaterial`s; both use the same material plugin and state textures, with a shader define separating their cached terrain and water variants. Water adds at most one colour pass per water-bearing chunk, not per voxel or tile. The plugin adds per-voxel colour grain on solids, explored dimming, the reachable-range tint and territory tint, plus flat unlit fog. It reads two small state textures: a **width × height tile-state texture** (R explored, G reachable, B territory, A charted) and a **column texture** holding the owning tile's state for every voxel column. Grid, range and territory shader overlays stay on land tops, never on the submerged floor or open water; separate selection/hover rings can mark the level water cap. The land grid fades further when zoomed out; selection, reachable outline and territory border remain distinct. The territory byte (`territoryCode`) carries the owner plus one bit per hex edge where the territory ends. Explored dimming, ranges and borders update in place; newly charted terrain remeshes only affected chunks, including the outer shelf radius.
- **Actual underwater voxel relief, not painted square facets.** The maintainer's Ist/Soll comparison rejected the former opaque patterned plane. Charted-land distance determines a continuous seabed depth, warped by deterministic broad/fine noise; depth therefore follows irregular coves rather than drawing even rings. The seabed shows pale sand in the shallows, patchy sand/stone on the shoal, muted stone at the shelf and a deep blue floor. Every seabed material, including deep blue, uses the water-floor face flag so it never inherits the land grid. Sparse seeded outcrops rise from it. Real top and side faces remain visible through a level alpha-blended cap (alpha 0.4); the open-water hex grid is suppressed so the underwater forms read first. Terrain and water material plugins share logic but have distinct shader-cache defines, preserving their different grid behavior. Water colour and softened underwater lighting support, rather than paint over, the geometry. Cut walls remain opaque blue. Only **charted** land shapes the depth field, and unknown tiles contain no seabed or rocks. Scale 2 omits coastal relief and outcrops to preserve large-map budgets. There are no dynamic waves, refraction, water physics or gameplay depth changes. Tests verify multiple floor heights and materials, submerged side faces and rocks, exact constant-height cap coverage, opaque/transparent index separation, hidden-coast protection, outer-shelf invalidation and unchanged water picking; a browser check verifies visible water detail in the framebuffer.
- Lighting is a hemispheric fill and a directional sun with one 1024² PCF shadow map. The shadow map uses a 16-bit single-channel colour target plus 32-bit depth, about 6 MiB, fixed and independent of map size. Opaque terrain and submerged solids cast shadows; the transparent cap does not. The map is redrawn only after map changes or remeshing once shaders are ready, not every frame. Chunk vertex/index buffers are about 34.5 MiB for the fine showcase (723,828 vertices), 35.2 MiB at 64² (738,136) and 16.2 MiB at 256² (339,920), excluding shadows, state textures and CPU copies. Coastal cap-colour boundaries split some greedy quads but do not alter relief, mesh counts or materials. All three measured fixtures have **56 chunks + 2 markers = 58 meshes, 6 materials** (terrain, water, figures, rival ring, hover, selection), plus the shared `MultiMaterial`. Geometry counts remain equal to mesh counts. The finer showcase deliberately raises its former 250k vertex ceiling to the existing larger-fixture ceiling of 900k; all three sizes must stay below it.
- **Surface material shades supplement geometry.** The material plugin combines two smooth procedural patch fields with per-cell grain, quantizes them into five tones and applies material-specific RGB multipliers to upward-facing land and water-cap faces. This replaces the overly uniform surface reading without changing the accepted seabed. Cells are anchored in global voxel-column space, continuous across hex and chunk boundaries: one voxel on ground, 2 by 2 voxels on water to avoid fine visual noise. Derivative-based filtering fades their contrast as they become subpixel, and the shoreline receives only 35% of the contrast. Existing solid grain, baked occlusion, lighting and real underwater relief remain; decorations and opaque fog are excluded, and territory/reachable overlays apply afterward. No image texture, additional geometry, state texture, animation or rules/PRNG change is introduced. Browser framebuffer tests check water/grass tonal spread, flat colour inside cells, camera-independent world anchoring and unchanged vertex/buffer counts. The grass test also checks the interquartile colour range so isolated tufts or stones cannot masquerade as surface shading.
- **Rendering on demand.** The map has no animation, so the render loop draws a frame only after something changed: camera, markers, map, fog, figures or canvas size all call `invalidate()`. It keeps drawing while shaders compile and refreshes the one-shot shadow map once the scene is ready. Idle turns therefore cost no GPU time, which matters for phone batteries and for several open matches. New code that changes the scene must call `invalidate()`.
- **Framebuffer-calibrated palette.** The approved concept calls for yellow-green grass, cyan shallows and saturated deep blue, pale sand, warm grey stone, olive/forest foliage and terracotta roofs. Calibrate the final rendered colour, not raw palette RGB: vertex occlusion, lighting, material tones and alpha blending all affect it. Fixed 32² browser samples target concept medians `[151,171,60]` for grass and `[11,117,170]` for deep water, with an eight-byte per-channel tolerance; measured values are `[151,170,60]` and `[11,118,172]`. Shadowed coasts and different compositions are not pixel-identical illustration samples. The cap uses distinct shallow/shoal/shelf/deep palette kinds chosen from the existing charted-only coastal classification. They all retain the water-surface face role, material and level; a single dark blue alpha-0.4 cap could not also reproduce bright cyan shallows. Coastal caps disappear when their source coast is uncharted and are omitted at scale 2. Water tone contrast compensates for the darker deep-blue base without changing its mean.
- **Thin, antialiased frames.** For each hex-edge direction, compute the Euclidean screen-pixel footprint from derivatives of continuous world coordinates before branching; never differentiate rounded hex-local coordinates. A coverage hairline replaces the old broad grid smoothstep, giving measured 1–1.25-pixel full width at half maximum at two inspection zoom levels (test ceiling 1.5 pixels). A negative control with the old shader measured 3.5 pixels and failed. Reachable bands are 0.012 world units wide; territory bands 0.032, their dark seam 0.043 and restrained glow 0.12. These use the same pixel-aware coverage but keep their faction/interaction identity. Hover rings span 0.95–0.98 of the hex corner radius, selection 0.92–0.98 and rival dashes 0.9–0.97. Framebuffer profiles test all three edge orientations, visible contrast and the absence of a broad halo; gameplay tests retain scout readability and selection behavior.
- **Units and cities.** Units are small voxel figures (`src/rendering/figures.ts`, 1/24-unit voxels, cached per kind and faction) standing on the visible voxel under their feet; several units on one hex stand side by side. Rival units also get a dashed red hex ring. Each visible city gets an HTML name plate with its population above the keep, positioned from the camera matrices after every camera change.
- Picking does not ray-cast meshes. The renderer keeps a per-tile surface height, which is the fog height for unseen tiles. `pickTile` walks the camera ray through the voxel columns (2D DDA) and returns the canonical ID of the hex owning the first column the ray enters at or below its tile's surface. Unit tests check it against a brute-force intersection. Decorations never intercept picks, and identity never derives from draw order.
- Separate selection overlays from terrain chunks; hex-ring markers and unit figures render in a later rendering group so trees cannot hide them.
- Fixed orthographic camera at **yaw 45°, pitch `atan(1/sqrt(2))` (35.264°)**, no rotation. This replaces the former 60°/42° view at the maintainer's request: equal cube-axis lengths and symmetric 30° screen slopes follow the approved concept's isometric construction. The illustration has no camera metadata and contains local projection variation, so these values are a calibrated consistent projection, not a claim that one exact source camera was recovered. `src/rendering/view.ts` supplies the shared basis for camera/pan/framing, tree placement and figure facing; picking tests use the same view. Browser tests independently measure actual projected axis lengths and slopes. Movement buttons keep their six relative directions, but hex edges are no longer forced vertical/horizontal on screen; the lower view can correctly hide low terrain behind higher foreground terrain. Pan target clamps to the hex centres (`0..width-½` in x, `0..(height-1)·√3/2` in z), with no outside padding. Zoom half-height clamps from 3 world units to an aspect-correct whole-map fit with 2 units of framing margin. Resize preserves the relative zoom. Ray intersection/pick results go through the mapping adapter, then domain bounds validation.
- Dispose old chunk meshes, both state textures, figures, name plates, listeners and selection on regeneration. Clear stale picks and selection before showing a replacement map.
- Detect missing WebGL2 and display a useful fallback message rather than an empty canvas.

### Future incremental work and simulation costs

Implemented fog is a faction-owned sparse immutable record of explored/visible tile IDs; absent entries are unseen. Terrain is immutable, so the map itself is the remembered terrain source. Moving copies the discovered record, processes old/new/traveled sight regions (not every map tile) and returns only changed visibility IDs. End-turn and camera motion do not alter fog. Mutable last-known terrain and enemy-unit hiding remain brief 11 work.

Unseen tiles are meshed as one flat slab at a uniform fog height and colour. They have no terrain-dependent height, silhouette, shadow, occlusion, trees or picking result. Only charted neighbours shape a tile's rim (beaches, shallows), and trees grow only from charted tiles, so known land never outlines hidden terrain. Explored dimming, reachable tiles and territory borders come from the state textures, updated in place, so remembering terrain, showing ranges and moving borders never remesh. When tiles become charted or gain a settlement, only chunks within tree or coastal-shelf reach of them are remeshed (`affectedChunks`), in place; mesh and geometry counts stay constant. Full mode transitions and regeneration initialize all tiles. Unit figures and rival rings are separate non-pickable meshes rendered above the terrain and are disposed on every exploration update, on leaving the expedition and on regeneration. No per-tile meshes or per-frame visibility computations are added.

Pathfinding should start with deterministic A* for a single destination and Dijkstra for movement ranges. On a hex grid every tile has at most six edges, so edges scale with tile count; heap-based searches can approach O(V log V) and O(V) memory. Repeating a full search for every unit/candidate can dominate AI turns. Bound AI candidate sets and search counts, reuse valid results with explicit terrain/occupancy invalidation, and measure expanded nodes and per-turn work. Defer Web Workers until profiling shows main-thread stalls justify serialization and coordination costs. If introduced, use immutable inputs, explicit RNG state and ordered results; worker scheduling must not alter outcomes. This refers to browser threads, not gameplay worker units.

## ADR-005: serverless play by messenger

**Decision:** two players exchange finished turns as text through any messenger, e-mail or file. A turn message is a **match package**: the complete ordered command log of the match so far plus what is needed to rebuild the world, never a snapshot of state.

```text
MatchPackage { format, matchId, rules, generator, seed, width, height, factions, commands[], mapHash, stateHash }
```

- **Replay, not state.** The receiver regenerates the map from seed and generator version and replays every command through `applyCommand`. This relies on ADR-002: integer arithmetic, explicit tie-breaks, no wall time and no randomness in commands. `mapHash` (hash of the generated tiles) proves both devices built the same world; `stateHash` (canonical hash of the replayed state, fog included) proves they reached the same position. A mismatch is refused with a reason and never half-applied.
- **Turn discipline.** `MATCH_FACTIONS` fixes the order: the host plays Meridian and moves first, the guest plays Lantern. A received package must end with `end-turn`, extend the local log of the same `matchId` (the shared prefix must be identical) and contain no orders for the receiver's own faction. Equal or shorter logs are reported as already known. Duplicates, reordering and lost messages are therefore harmless: the newest package supersedes everything before it, and an opponent's message can also start a match on a device that has never seen it.
- **Several matches.** The receiver reads the `matchId` before replaying and checks the package against that match's saved log, whichever match is on screen; an unknown `matchId` starts a new match. So any number of matches run side by side without the player sorting messages. The list of saved matches reads only the package shape and counts `end-turn` orders for round and active side (`matchProgress`); the full replay happens when a match is opened.
- **Untrusted input.** Packages are pasted text: caps on text (1.5 M characters) and decompressed JSON (1 MB), at most 10,000 orders, strict shape and identifier checks before the world is allocated, and the usual seed/dimension contract. Compact orders are re-validated by the normal rules during replay.
- **Encoding.** `polaris1z.<base64url(deflate-raw(JSON))>` with `CompressionStream`, falling back to `polaris1j.<base64url(JSON)>`. The decoder also accepts a link (`#turn=` fragment), a chat message around a code, or the JSON of a saved file. The prefix and `format` leave room for later versions. The fragment never reaches a web server.
- **Persistence.** Each match is stored as a package with the player's faction and an optional local name under its own `localStorage` key `polaris.matches.v1.<matchId>`; `polaris.current-match.v1` names the match that reopens after a reload. A match is replayed and verified when it is opened and discarded with a visible reason if it no longer verifies. The single match of earlier versions (`polaris.match.v1`) is migrated on start. The outbox is derived from state and faction instead of stored, so a reload offers the identical link.
- **Presentation.** `main.ts` remains the composition root. The viewer faction decides what is rendered (own fog, own scout, own reachable tiles) and whether orders are accepted; `src/game` knows nothing about devices or messengers.

| Alternative | Why not now |
| --- | --- |
| Hot-seat on one device | Two people cannot play remotely; rejected by the project owner |
| WebRTC or Bluetooth | Needs a live peer and a signalling exchange that is itself a copy-and-paste step; NAT and browser support add complexity |
| Relay or lobby server | Adds hosting, accounts, abuse handling and cost before the rules justify it; remains the path for secrets, simultaneous turns and notifications |

**Consequences and risks**

- No anti-cheat: both devices know everything, fog is presentation, checksums only detect accidents. Both players need the same game, rules and generator version; a mismatch is reported.
- The generator uses `Math.sin`, `Math.cos`, `Math.hypot` and `Math.sqrt`, whose last bits are not guaranteed identical across JavaScript engines (for example Chromium and Safari). Tile classification would only flip on a near-tie, and `mapHash` turns any such divergence into an explicit refusal at join time instead of a silent desync. Cross-engine play should still be tested on real devices; a table- or integer-based replacement needs a generator version bump and new fixtures.
- Links grow with the log. A file export is the fallback for chats that cut messages; delta packages (only the new orders plus a checksum of the shared prefix) are the next optimization if logs get long.
- Revisit with a server when hidden information, more than two players, asynchronous notifications or ranked play become requirements. The command log and checksums carry over unchanged.

## Benchmark protocol

**Initial evidence:** the first benchmark here will be a shorter software-rendered runner sample, not the full protocol below. Report its actual duration, sample count, software renderer, environment and limitations alongside results. Do not extrapolate it to hardware-rendered desktop/mobile performance, sustained frame rates, or leak-free operation. No numbers below are measurements.

**Future full protocol:** use the **32 × 32 showcase** and **256 × 256 stress fixture**, with fixed published seeds and generator version. Record browser/version, OS, CPU/GPU, RAM, viewport, device-pixel ratio, power mode, build mode, and commit. Test a production build on named desktop and mobile-class reference devices; runner results are not a device baseline.

After warm-up, perform five regenerations and a repeatable 30-second pan/zoom/pick path. Report median and worst generation-to-interactive time, p50/p95 frame duration, pick latency, draw calls, instance counts, and available memory indicators. Capture cold-load separately. Repeat regeneration 20 times to check retained resources; distinguish noisy browser memory indicators from verified leaks.

**Provisional targets, not measured results:** these apply to the eventual named desktop baseline; mobile budgets await measurements.

| Metric | 32 × 32 showcase | 256 × 256 stress | Measurement boundary |
| --- | --- | --- | --- |
| Map generation only, p95 | ≤25 ms | ≤250 ms | Pure domain generation; excludes scene upload and first frame |
| Generation-to-interactive | ≤1 s | ≤3 s | Includes generation, upload and first usable frame |
| Interaction frame duration, p95 | ≤33 ms | ≤50 ms | Warm pan/zoom/pick path |
| Pick-to-inspector, p95 | ≤100 ms | ≤100 ms | Input to visible inspector update |
| Map-attributable retained JS heap | ≤32 MiB | ≤128 MiB | Settled map minus empty-app baseline; report availability/noise |
| Estimated map GPU allocations | ≤16 MiB | ≤64 MiB | Buffers/textures counted separately from JS heap; not total browser memory |
| Draw calls per frame | ≤20 | ≤800 | Terrain and markers; the on-demand shadow-map pass is excluded. Instrument, do not infer from mesh count |
| Future turn resolution, p95 | ≤100 ms | ≤500 ms | Domain + one AI faction; fixed fixture of 100 total units/10 cities; excludes animation/rendering |

Future turn budgets are unimplemented targets, not generator performance claims. Publish actual numbers, fixture details and gaps before calling any target met. Optimize only demonstrated bottlenecks while retaining deterministic fixtures and correct picking.
